# 跨库引用

> 上位：`README.md` ｜ 相邻：`影响面.md` §2.4
> 本文只讲一件事：**改本库结构时，别的库怎么不断链**。

---

## 1. 为什么单列一篇

改结构的人只看得见自己的库。引用方在另一个目录、另一个工位、甚至另一台设备上，改完不会有人通知他。

而且这类断链**零报错**：表里存的是字符串不是链接，Excel 不报错、编辑器不报错、脚本不跑就永远不知道。

---

## 2. 实测事故：591 条路径静默两个月

| 项 | 内容 |
| :--- | :--- |
| 时间 | 2026-11-11 改，2026-11-12 20:15 才发现并修完 |
| 改动方 | 母体 B 的 `00_资源库`：`01_角色/立绘SI\|头像\|立绘HD/` → `10_用户层/11_角色立绘/` |
| 受害方 | 母体 A 的 `素材清单` |
| 规模 | **199 行 / 591 条路径全部指空** |
| 为什么没发现 | 表里是字符串，不是超链接 |
| 修复 | 重定基 4 组前缀 + 补 10 角色 + 修 6 条存量脏路径 → 209 行、**627/627 可达** |

同一时期，母体 A 的 `角色辞典.json` 还有 **598 处**资源引用，也是靠事后补检才确认全通。

### 2.1 教训

1. **改结构必须广播**。不是「我改完了」，而是「我改了哪些前缀，引用方请跟」。
2. **跨库引用必须进常态化体检**。不能靠人记得。
3. **引用方一旦被漏，损失按表行数计算**。591 条意味着 199 个角色没有素材可看。

---

## 3. 三条处置原则

### 3.1 改前广播，列出前缀映射

给引用方的信息只要三样：

| 项 | 例 |
| :--- | :--- |
| 旧前缀 → 新前缀 | `01_角色/立绘HD/` → `10_用户层/11_角色立绘/` |
| 生效时间 | 2026-11-11 |
| 影响判据 | 表里含 `01_角色` 的行全部失效 |

不要发「资源库结构优化完成」这种话——它无法让引用方定位到自己要改哪几行。

### 3.2 引用方存相对路径，不存绝对路径

| 做法 | 换设备后 |
| :--- | :--- |
| 表里存 `10_用户层/11_角色立绘/2B_c810_00.png` | 只需改根，全表自动对 |
| 表里存 `F:\Codex\Nikke\01_母体\...\2B_c810_00.png` | 每一行都要改 |

现存的取件表已经是相对口径（`local` 列 = 相对库根），这是正确做法。

### 3.3 引用方必须有体检脚本

`tools/check_table_paths.py` 就是干这个的：

```bash
python tools/check_table_paths.py                    # 扫配置里的目标表
python tools/check_table_paths.py --files a.csv b.csv
python tools/check_table_paths.py --limit 0          # 列出全部不可达
```

退出码 0 = 全可达。

**调用时机**：改结构后跑一次；日常每月一次；CI 里每次提交跑一次。

## 4. 跨库引用的三种形态

| 形态 | 例子 | 断链风险 | 处置 |
| :--- | :--- | :-: | :--- |
| **表内路径**（字符串） | 素材清单 xlsx、角色辞典 json | 高，零报错 | 体检脚本 |
| **代码常量** | 别的工作位 `LIB = ".../00_资源库"` | 中，跑起来才报错 | 改走 `libpath.py` |
| **硬链接 / 快捷方式** | `.lnk`、目录 junction | 中，点开才知道 | 逐个人工验证 |

**最高危的是第一种**，因为它同时也是数量最大的一种。

---

## 5. 引用方自查清单

收到结构变更通知后，按这个顺序过：

| # | 检查 | 命令 / 方法 |
| :-: | :--- | :--- |
| 1 | 表里有没有旧前缀 | Excel 筛选 或 `grep` |
| 2 | 代码里有没有旧前缀 | `grep -rn "旧前缀" --include=*.py .` |
| 3 | 路径列是相对还是绝对 | 打开表看前 5 行 |
| 4 | 改完跑体检 | `python tools/check_table_paths.py` |
| 5 | 记一笔到本工位记忆 | 防下次再漏 |

第 5 步不是形式主义：**同一处漏改过两次的概率远高于零**。

---

## 6. 体检结果怎么读：不可达要分三类

`check_table_paths.py` 报「不可达」时，不要一律当错误修。实测 2026-11-14 全量 14 份登记表：
**8,629 条可达 / 151 条不可达**，而这 151 条里真正需要动的只占一部分。

| 类型 | 特征 | 数量级 | 处置 |
| :--- | :--- | :--- | :--- |
| **A 前缀失效** | 整表大面积不可达，路径前缀还是旧的 | 数千条 | **必须修** `legacy_prefix` 映射 |
| **B 内容撤下** | 零星不可达，文件名多带 `_intl` 等来源标记 | 上百条 | **不修**。文件被后续流程撤下/替换，属正常历史状态 |
| **C 登记错误** | 单条不可达，同类其他条目都可达 | 个位数 | 修表或补文件 |

判定口诀：**看比例，不看单条**。一张表 100% 不可达 = 前缀问题；100 条里 3 条 = 内容变更。

### 6.1 B 类为什么不该修

实测那 151 条里，带 `_intl` 后缀的占绝大多数。这批文件来自国际服全量采集，后续按「保留国服、撤下重复 intl」的收敛流程处理过——**文件确实不在了，但登记记录是当时的事实**。

把登记表改成「文件现在在哪」，等于把「这批采过什么」抹掉。正确做法是在表外加一份说明，而不是改历史行。

> 这与 `01_标准\红线与例外.md` §3「存量不追溯」是同一条原则。

### 6.2 前缀映射的边界

`legacy_prefix` 只能做**前缀级**映射。域内子目录的重组它管不到：

```
旧：09_音频/03_未归属曲库/xxx.wav
新：10_用户层/19_音频/未归属曲库/xxx.wav     ← 子目录名去掉了 03_ 前缀
```

这类要靠人工细化配置，或者单独跑一次备份表。**不要指望一个映射表覆盖所有历史重组**——这是工具的边界，写在这里以免下次误判。

### 6.3 目录级登记表

若某张表的路径列存的是**目录**而非文件（如 `入库登记_20261104_骨骼.csv` 的 `库内目录` 列），体检会显示「可达 0」——因为脚本按「有扩展名的文件路径」判定，目录行被跳过。

这**不是故障**。要体检目录级登记，改成逐文件表或另写脚本。
