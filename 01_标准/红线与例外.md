## 1. 四条红线

| # | 红线 | 为什么（都有实例） |
| :-: | :--- | :--- |
| 1 | **不改叶子的业务名** | 客户端技术名一旦改，取件脚本全断。`icons-char-full(sd)` 改一个字，62 组图标全部定位失败 |
| 2 | **同一份东西不在两层各存一份** | 插画大礼包白占 **16.34 GB**，核对后确认是 `插画HD + 背景HD + 大厅背景` 的完整副本 |
| 3 | **迁移必须可回滚** | 15 万文件搬错一次，人工核对不可能。R1 回滚靠反向 20 次 `mv`，20 秒完成 |
| 4 | **层内不新增根级散文件** | 散件是历次混乱的起点。`06_骨骼` 根下曾混入 15 个脚本，最终只能靠新建 `27_处理工具` 收容 |

### 1.1 红线的边界

红线 1 只管**叶子**。域这一级改名是允许的（`06_骨骼` → `26_合成原料`），因为改名时同批改了映射表与调用方。

红线 4 的「散文件」指**代码与配置**。每个域内允许有 `README.md` 说明本域内容。

## 2. 例外登记

标准不可能穷尽所有情况。例外必须**登记**，不登记的超标一律视为缺陷。

### 2.1 登记三要素

| 要素 | 要求 |
| :--- | :--- |
| 依据 | 为什么这一层 / 这个目录是有效的，不是工具残留 |
| 范围 | 精确到目录，不许写「某类目录」 |
| 复审条件 | 什么情况下这个例外可以取消 |

### 2.2 现有例外（NIKKE 实装，长期有效）

| 对象 | 依据 | 复审条件 |
| :--- | :--- | :--- |
| `22_文本库\剧情正文\{主线,活动,支线,珍藏品剧情,妮姬Episode,其他}\` | 深 4 层，但实测是**有效分组**：活动 75 个子目录中 31 个装 15 文件、妮姬Episode 142 个中 136 个装 5 文件。拆掉会摧毁「多章合并为一个活动」的结构 | 剧情存储改为数据库 |
| `26_合成原料\骨骼\` 各角色组 | `.atlas` 首行写的是**同目录相对文件名**（如 `c810_01.png`），扁平即断 | Spine 运行时支持子目录引用 |
| `20_开发层\` 编号空 `24_` | 规划过但需求没落定，不占位 | 需求确定 |

### 2.3 例外失效的信号

出现以下任一情况，例外应重新评估：

- 目录内文件数降到 3 以下（说明已不是「有效分组」）
- 该层是导出工具产物（`export` / `Sprite` / `Texture2D` / hash）
- 有更强的判据能一句话说清归属
