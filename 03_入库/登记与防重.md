## 1. 登记表回答什么

只回答一件事：**这个文件是不是入过库**。

其余列都是为了让这个答案更可信：

| 要回答 | 靠哪列 |
| :--- | :--- |
| 入过库吗 | `库内路径`（唯一真正必需） |
| 哪一批来的 | 文件名日期 + `来源桶` |
| 和另一个同名文件是同一份吗 | `MD5` |
| 从哪个资源键提出来 | `资源键` / `资源类别` |
| 当时多大 | `字节` |

## 2. 表头必须收口（这是真实技术债）

现行 14 份 `入库登记_*.csv` 有 **4 套不同表头**，连「路径」列都有两种叫法：

| 批次 | 表头 |
| :--- | :--- |
| `入库登记_20261029.csv`、`_20261105.csv` | `入库日期,版本,资源类别,资源键,落盘相对路径,像素,字节,MD5` |
| `入库登记_20261104_背景插画.csv` | `类别,资源键名,尺寸,库内路径,来源资源键` |
| `入库登记_20261104_整族图标.csv` | `资源组,文件名,字节,库内路径` |
| `入库登记_20261104_骨骼.csv` | `分类,skel名,文件名,字节,库内路径,来源桶,包前缀` |

后果：任何「扫全库登记表」的脚本都得写四套分支，且**「落盘相对路径」与「库内路径」是同义词这件事没人知道**。

### 2.1 收口后的表头

```csv
入库日期,批次,资源类别,资源键,文件名,库内路径,字节,MD5,来源桶
```

| 列 | 必填 | 说明 |
| :--- | :-: | :--- |
| `入库日期` | ✅ | `YYYY-MM-DD` |
| `批次` | | 人可读的批次名，如 `骨骼`、`整族图标` |
| `资源类别` | | 上层分类，如 `技能过场`、`背景插画` |
| `资源键` | | 客户端资源键，用于追源 |
| `文件名` | ✅ | 含扩展名 |
| `库内路径` | ✅ | **相对库根**，正斜杠，如 `10_用户层/11_角色立绘/2B_c810_00.png` |
| `字节` | | 整数 |
| `MD5` | | 32 位小写；有同名文件时必填 |
| `来源桶` | | `core` / `intl` / `cn` 等 |

### 2.2 为什么统一叫 `库内路径`

三个理由，按重要性：

1. **它和取件表对齐**——取件表的 `local` 列就是相对库根的路径，同一语义应当同一措辞
2. 「落盘相对路径」有歧义：相对谁？相对采集目录也是「相对」
3. 它是唯一真正必需的列，值得一个不会误解的名字

### 2.3 存量怎么办

**不追溯。** 旧文件一字不改——改历史台账等于伪造记录。

新表从 `2026-11-14` 起按新表头；跨批次查询时用下面的兼容映射：

| 旧列名 | 新列名 |
| :--- | :--- |
| `落盘相对路径` | `库内路径` |
| `类别` | `资源类别` |
| `资源键名` | `资源键` |
| `尺寸` | `像素` |
| `资源组` | `资源类别` |
| `skel名` | `批次` 的一部分 |

## 3. 文件命名

```
入库登记_<YYYYMMDD>[_<批次>].csv
```

| 规则 | 说明 |
| :--- | :--- |
| 按批次分文件 | 一次采集一个文件，**不追加到旧文件** |
| `.bak` 只作备份后缀 | 避免被 `入库登记_*.csv` 通配误扫 |
| 日期是**采集日期** | 不是入库日期（跨天很常见） |

**为什么按批次而不是按月**：按月会让「这批是什么时候采的」无法回答；按批次能直接对上采集日志。

---

## 4. 滚动类文件只留最新 1 份

有些文件是「当前状态快照」而非「历史累积」，留着多份会让人不知道该看哪份。

| 类型 | 保留策略 | 实测 |
| :--- | :--- | :--- |
| `取件表_*.csv/json` | **只留最新 1 组**，旧版当次移回收站 | 曾有 5 个日期版本，20261105 与 20261110 内容 md5 完全相同 |
| `命名修正映射_*.csv` | **只留最新 1 份**，脚本按 mtime 取最新 | 曾有 5 份，含 dry-run 前版 |
| `入库登记_*.csv` | **全部并列**，不互相覆盖 | 14 份 |
| 审计报告类 | 永久保留 | 被规范引用后不能删 |

判定口诀：**「读哪份」有唯一答案的是滚动；「有哪些批次」有意义的是累积。**

## 5. 防重

### 5.1 三道防线

| 防线 | 时机 | 手段 |
| :-: | :--- | :--- |
| 采集前 | 最省事 | 查 `入库登记` + `已采集清单` |
| 落盘前 | 次省事 | 目标路径已存在 → 停下比对 MD5 |
| 定期 | 兜底 | 全库 MD5 分组，同组多于 1 份的报警 |

### 5.2 去重优先级（血的教训）

做全局去重时，**保留优先级不能靠目录新旧**，必须显式定序：

```
母体资源库(10) < 母体其他(15) < 工位产物(20) < 工位其他(30) < 临时车间(50) < 回收站(80) < 归档(90)
```

数字小的优先保留。

**实测事故**：去重优先级把「临时车间」排在「母体资源库」之上，导致 `00_资源库\01_角色` 的部分立绘被当成冗余移走，只能全量回滚。

**第二起**：备份目录与被备份目录同 MD5，优先级判定错误，把 Bot 的 `plot_docs.jsonl` 当重复副本移走，剧情索引从 2,514 条掉到 0 条。

> **口诀：去重时「活体/母体」永远排在「备份/临时」之上。**

### 5.3 什么时候不该去重

| 情况 | 处理 |
| :--- | :--- |
| 同名但 MD5 不同 | 两处各自保留（不同批次提取，像素可能有差） |
| 共享贴图在多个组里各一份 | 抽公共会破坏「每组 3~7 个部件」的规律 → **不抽**（实测 539 份 / 19 MB，接受） |
| `Sprite` 与 `Texture2D` 同源 | **不是重复**：一个是裁过透明边的切片，一个是全画布 |
| 文件名带 `_tex` 后缀的国服原生件 | **不是重复**：`_tex` 是国服原生后缀，`_intl` 才是人工加的 |
